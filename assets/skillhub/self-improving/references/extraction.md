# 经验抽取

## 信号清单

出现以下任一信号，说明本轮有东西值得记（在任务进行中记录，别留到结束后回忆）：

1. **多次试错**：连续 3 次以上尝试才命中，或前几次方向都是错的。
2. **被纠正**：用户说"不是这个""方向错了"，或事实否定了已做的判断。
3. **必须读源码/查规范**：结论无法靠通用知识得出，得翻库实现、读 RFC 或规范条款。
4. **反直觉**：正确做法与"看起来该这样"相反（例如某 API 的实际行为与文档描述不一致）。
5. **隐式依赖**：改动依赖库的未写明约定、框架内部顺序、CSS 计算规则、构建缓存行为。
6. **用户原话约束**：用户表达了长期偏好或红线（"以后都这样""不要恢复某做法"）。
7. **同一坑第二次出现**：之前记过类似现象，说明检索失败，需要补强条目或索引关键词。

## 价值判定五问

命中两条以上才落盘：

1. 下次遇到同类现象，靠它能少走一次试错吗？
2. 结论是否依赖本仓库的特定结构、版本或环境？
3. 是否存在"看起来该这样、实际不能这样"的坑？
4. 是否涉及用户明确表达的偏好或红线？
5. 不记的话，下次是否只能重新读一遍源码才能得出同样结论？

## 从哪挖事实

| 事实类型 | 来源 | 取法 |
|----------|------|------|
| 错误原文 | 终端输出、日志、截图 | 取完整首行 + 关键栈行，不转述 |
| 代码事实 | 源码、`git diff`、配置 | 记 `路径:行号`、函数名、配置项名 |
| 版本事实 | `package.json`、`go.mod`、About 面板 | 记精确版本号 |
| 规范事实 | MDN、RFC、库 CHANGELOG | 记条款或条目名，附 URL |
| 用户约束 | 对话原话 | 原样保留，不改写 |

## 不值得沉淀

- 一次性笔误、拼写、变量名写错。
- 未查明根因的环境抖动（重启就好了之类）。
- 一次 grep 就能得到的信息：某个函数在哪、某个字段叫什么。
- 代码和注释已经说清楚的内容（重复注释没有增量）。
- 纯粹的业务数据或一次性配置值。
- 尚未验证的推测（可以留作待验证清单，但不写成根因）。

## 抽取时机

- 主任务完成后立刻做，此时上下文完整。
- 任务中途发现重大根因：先在主线里把根因讲清楚，任务收尾时再落盘，不在中途切出去写文档。
- 一轮长会话结束时：回看本轮的试错序列和纠正点，逐条过价值判定五问。
