
## maxGraph API 迁移修复（GraphCanvas.tsx，14 个 TS 错误 → 0）

`src/components/editor/nodes/graph/GraphCanvas.tsx` 原用了旧 mxGraph API，在 maxGraph 下报 14 个 TS 错误。根因与修法：

1. **`graph.createSelectionShape` 已不存在** → 选中框创建逻辑迁到 `VertexHandler.prototype.createSelectionShape(bounds)`。
   - 签名从 `(state: CellState)` 变为 `(bounds: Rectangle)`；cell 状态改用 `this.state`。
   - 颜色/线宽/虚线改读 `this.getSelectionColor()` / `getSelectionStrokeWidth()` / `isSelectionDashed()`（底层即 `VertexHandlerConfig`，随主题自动更新，无需 `darkModeRef`）。
   - bounds 用 `Rectangle.fromRectangle(bounds)` 克隆（与官方默认实现一致）。

2. **Shape 属性改名**：`dashed`→`isDashed`、`fillColor`→`fill`、`strokeColor`→`stroke`。

3. **Shape 构造参数类型修正**：第 3 参数 stroke 应为 string（旧代码误传 `1`）。统一 `new XShape(bounds, 'none', color, strokeWidth)`。

4. **`CellState` 无 `bounds` 字段**：`CellState extends Rectangle`，本身即 bounds；选中框用传入的 `bounds` 参数即可。

5. **`ConstraintHandler.pointImage` / `highlightColor` 现为实例属性（非静态）**：经 `graph.getPlugin<ConnectionHandler>('ConnectionHandler')?.constraintHandler` 取实例设置。两处（init effect + dark effect）同改。

import 调整：`type VertexHandler`→值导入（用 `.prototype`）；新增 `Rectangle`、`type ConnectionHandler`；移除不再使用的 `ConstraintHandler` 值导入。

验证：`npx tsc -b --noEmit` exit 0（`npm run build` 因 vite 清理 dist/assets 被沙箱拦截，但 TS 类型检查已全过）。

## 文档切换渲染串台 bug 排查（BlockEditor.tsx，dev-only）

**症状**：新建文档 A → 打开文档 B → 切回 A，A 的编辑区显示 B 的内容（仅渲染，未落库）。**仅 `npm run tauri dev` 复现，`make install` 无此 bug** → 指向 React StrictMode（生产构建不双调用 effect）。

**静态分析结论**：store 逻辑（`openDocument` 原子 set `activeDoc`+`activeDocId`、`setActiveDocBlocks`/`flushBlocksToDoc` 的 ownership guard、TipTap `setContent` 同步派发事务）均正确。切回 A 时守卫 `loadedDocIdRef(B) !== activeDocId(A)` 必然放行 setContent(A)，理论应显示 A。故根因是运行时行为，非静态逻辑错误。

**最可能机制**：TipTap v3 `useEditor` 在 StrictMode 下构造函数 `scheduleDestroy`（1ms 延迟销毁）可能抢在 post-paint 的 `useEffect`（`clearTimeout` 取消销毁）之前触发，导致 editor 实例被销毁重建；而 `loadedDocIdRef` 仍指向旧 doc id，守卫据此跳过对新实例的重新加载 → 新实例显示陈旧内容。

**已做改动**（`src/components/editor/BlockEditor.tsx`，本轮）：
1. 新增 `loadedEditorRef` 追踪"内容实际加载进哪个 editor 实例"；守卫改为 `loadedDocIdRef===activeDocId && loadedEditorRef===editor`，editor 实例变更即强制重载。在 static / hasActiveDoc / success / catch 四个分支同步维护该 ref。
2. blocks 读取改为按 `activeDocId` 从 `documents` 查找（原读 `activeDoc?.blocks`），消除任何 activeDoc 滞后于 activeDocId 的可能。
3. 加 TEMP 诊断 `[docswitch] enter/ok/skip` 日志（含 editorId、isDestroyed、blocksPreview 等），含模块级 `editorIdMap` WeakMap。**待用户 dev 复现并回贴控制台输出后确认根因，再决定是否保留日志。**

验证：`npx tsc --noEmit -p tsconfig.app.json` exit 0。

**待办**：等用户回贴 `[docswitch]` 日志确认实际触发路径；若证伪 editor 重建假设，需进一步排查。另可让用户临时去掉 `<StrictMode>`（main.tsx）作快速确认测试。

### 第三轮：用户贴出复现日志后的根因确认（15:37）

**用户控制台出现关键错误**（之前两轮没注意到的）：
```
[Error] flushSync was called from inside a lifecycle method. React cannot flush when React is already rendering.
```
栈：
```
commitHookEffectListMount → SectionEditor.tsx → method(tiptap command) → dispatchTransaction → updateState → updateChildren → addNode → create(NodeView) → ReactNodeView → mount → ReactRenderer → flushSync → ERROR
```

**真相大白**：用户运行的是 **SectionedBlockEditor**（`localStorage 'jstudio.sectioned' === '1'`），不是 BlockEditor！前两轮对 BlockEditor 的改动虽然正确（防御性加固），但**没碰到处 bug 的代码**。`make install` 没 bug 的原因也很可能是因为生产构建 localStorage 不同、用的是 BlockEditor 而非 SectionedBlockEditor。

**根因（第三个，真正的）**：`SectionEditor.tsx` 的加载 effect 里 `editor.commands.setContent(content)` 在 `useEffect` 里**同步调用**。当 content 含 NodeView 类型块（code block / image / file / link / diagram / table 等）时，ProseMirror 的 `updateChildren` 挂载 React NodeView → TipTap `ReactRenderer.mount()` 调 `flushSync` → 但此时 React 正在 commit 阶段（passive effects）→ 抛错 → 事务被中断 → editor 留下陈旧/部分内容。**这就是"切回新文档看到旧文档内容"的直接原因。**

**第四个问题（同类型）**：`SectionEditor` 的 `loadedRef = useRef(false)` 与 BlockEditor 的 `loadedDocIdRef` 有同样的 StrictMode 问题——ref 在 StrictMode 模拟 unmount/remount 间持久，remount 时 guard 跳过加载，新 editor 实例无内容。

**已做改动（第三轮）**：
1. `SectionEditor.tsx`：`loadedRef`→`loadedEditorRef`（追踪 editor 实例）；`setContent` + merge 逻辑整体包进 `queueMicrotask()` 移出 React commit 阶段，避免 flushSync 冲突；加 `isDestroyed` 守卫。
2. `BlockEditor.tsx`：主分支 + static 分支的 `setContent` 也包进 `queueMicrotask()`（同样的 flushSync 风险，防御性修复）；`loadedDocIdRef.current = targetDocId` 提前到同步段作为"加载中"标记防止并发。

验证：`npx tsc --noEmit -p tsconfig.app.json` exit 0。

**总结三个根因**：
1. ❌ BlockEditor `loadedDocIdRef` StrictMode（已修，但非真凶）
2. ❌ StarterKit v3 重复 link/underline（已修，独立 bug）
3. ✅ **`setContent` 在 `useEffect` 里同步调用 → `flushSync` 冲突**（真凶，已修 SectionEditor + BlockEditor）
4. ❌ SectionEditor `loadedRef` StrictMode（已修）

**待用户测试**：硬重载 dev → 复现 → 确认 flushSync 错误消失 + bug 消失。**另建议用户考虑关闭 sectioned editor POC**（`localStorage.removeItem('jstudio.sectioned')`），因为它是已知有 gap 的 POC。

### 第五轮：修复 POC 本身 + 清理诊断日志（19:23）

用户确认是 POC 导致的问题，问能否修复。可以。

**SectionEditor 最后一处隐患**：之前把 `loadedEditorRef.current = editor` 设在了同步段。StrictMode 第一次 effect 的 cleanup 会 cancel 掉 setTimeout，第二次 effect 发现 ref 已匹配 editor → 跳过 → **内容永远加载不进去**。修法：把 ref 赋值移到 setTimeout 回调内部（setContent 成功后才标记"已加载"）。这样 StrictMode 第一次的 timer 被 cleanup cancel，第二次重新 schedule timer 并真正执行加载。

**清理工作**：
- 删除 BlockEditor 里的 `editorIdMap` / `editorId()` 辅助函数 + 所有 `[docswitch]` 日志 + `[caret-dbg]` 点击日志。
- App.tsx 恢复 `localStorage.getItem('jstudio.sectioned')` POC 开关（POC 现在已修好，可以正常用）。
- 保留的改动：`setTimeout(0)` 延迟 setContent（BlockEditor + SectionEditor 都保留，防御 flushSync）；`loadedEditorRef` 实例追踪守卫（两者都保留）；StarterKit v3 去重 link/underline（三个文件都保留）。

验证：`npx tsc --noEmit` exit 0。

**总结**：POC 的 flushSync bug 有两层——(1) setContent 在 effect 里同步调用触发 flushSync 冲突 → 用 `setTimeout(0)` 延迟到下个宏任务；(2) StrictMode 下 ref 同步赋值导致第二次 effect 跳过加载 → 把 ref 赋值移到回调内部。两层都修好后 POC 可正常使用。
